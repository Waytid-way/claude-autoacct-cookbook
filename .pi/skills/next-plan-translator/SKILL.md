# Next Plan Translator

ก่อนเริ่มทำงาน Phase ถัดไป ให้หยุดการลงมือทำชั่วคราว แล้วอธิบาย “แผนงานถัดไป” ให้เข้าใจง่ายในระดับคนที่ต้องตัดสินใจและตรวจสอบงานได้ โดยแยก สิ่งที่ต้องทำจริง ออกจาก ศัพท์เทคนิค / แนวคิด / รายละเอียด implementation

เป้าหมายไม่ใช่การอธิบายว่า “ระบบทำงานอย่างไร” แต่คือการตอบให้ชัดว่า:

«Phase ถัดไปเราจะทำอะไร ต้องสร้างหรือเปลี่ยนอะไร มีจุดไหนต้องเลือก มีอะไรต้องตรวจสอบก่อน และอะไรคือเงื่อนไขที่จะถือว่าไป Phase ต่อไปได้»

กติกาหลัก

1. เริ่มจากภาพรวมของ Phase ก่อน อย่าเริ่มจากศัพท์เทคนิค
2. ใช้ภาษาง่ายที่สุดก่อน แล้วค่อยใส่ศัพท์เฉพาะในวงเล็บเมื่อจำเป็น
3. ห้ามใช้ศัพท์เฉพาะเป็นหัวข้อหลักโดยไม่แปลความหมาย
4. แยกให้ชัดระหว่าง:
   - สิ่งที่ “ต้องทำ”
   - สิ่งที่ “ต้องตัดสินใจ”
   - สิ่งที่ “ต้องตรวจสอบ”
   - สิ่งที่ “เป็นเพียงรายละเอียดทางเทคนิค”
5. ห้ามทำให้รายการที่ยังไม่แน่ใจดูเหมือนเป็นข้อสรุปแล้ว
6. ถ้ามีหลายทางเลือก ให้แสดงเป็น C / D / E พร้อมเหตุผลและ Trade-off แบบภาษาคน
7. อย่าเสนอทางเลือกใหม่ที่ไม่จำเป็น เพียงเพื่อให้รายการดูครบ
8. ถ้ายังมีข้อมูลไม่พอสำหรับการตัดสินใจ ให้ระบุว่า “ยังตัดสินใจไม่ได้” และบอกว่าต้องรู้อะไรก่อน
9. อย่าเริ่ม implementation จนกว่าจุดตัดสินใจและ pre-check ที่จำเป็นจะชัดเจน
10. แยก “ทำตอนนี้” ออกจาก “อาจต้องทำภายหลัง”

---

รูปแบบคำตอบที่ต้องใช้

1. ภาพรวม Phase ถัดไป

อธิบายเป็นภาษาคน 2–5 ประโยค:

«Phase A มีเป้าหมายคืออะไร?

เมื่อจบ Phase นี้ เราควรมีอะไรเพิ่มขึ้น / เปลี่ยนแปลงไป?

สิ่งนี้แก้ปัญหาอะไร?»

ห้ามลง implementation detail ในส่วนนี้

---

2. เราจะทำอะไรจริง ๆ

เขียนเป็นลำดับเหตุการณ์:

«Phase A
→ สร้าง B
→ เปลี่ยน C
→ เชื่อม D
→ ตรวจ E»

แต่ละข้อให้ตอบสั้น ๆ ว่า:

ทำอะไร:
ทำไปเพื่ออะไร:
ผลที่ควรได้:

อย่าใส่ศัพท์เทคนิคที่ไม่จำเป็น

---

3. สิ่งที่ “ต้องสร้าง / เปลี่ยน”

แยกจากแผนงานโดยรวมอย่างชัดเจน

สิ่ง| Action| เหตุผล| ผลลัพธ์ที่ต้องมี
B| สร้าง| เพราะ...| ...
C| แก้ไข| เพราะ...| ...
D| เชื่อมต่อ| เพราะ...| ...

หลักสำคัญ:

«ทุก item ต้องเป็นสิ่งที่ Agent สามารถชี้ไปยัง artifact จริงได้ เช่น file, module, test, config, interface, document หรือ behavior»

ห้ามใส่ concept ลอย ๆ เช่น “ปรับ architecture” โดยไม่บอกว่าจะปรับอะไร

---

4. จุดที่ “ยังต้องตัดสินใจ”

หาเฉพาะจุดที่มีหลายทางเลือกและการเลือกมีผลต่อ implementation

ตัวอย่าง:

Decision 1 — เลือก C หรือ D

C

- ทำแบบ...
- ข้อดี...
- ข้อเสีย...

D

- ทำแบบ...
- ข้อดี...
- ข้อเสีย...

ผลกระทบ

- ถ้าเลือก C → จะเกิด...
- ถ้าเลือก D → จะเกิด...

คำแนะนำตอนนี้: C เพราะ...

ถ้ายังไม่มีข้อมูลพอ:

«สถานะ: ยังตัดสินใจไม่ได้

ต้องตรวจสอบ X ก่อน เพราะ Y มีผลต่อการเลือก»

---

5. สิ่งที่ “ต้องตรวจสอบก่อนลงมือ”

นี่คือส่วนสำคัญที่สุด

แยกออกจากงาน implementation โดยเฉพาะ

สำหรับแต่ละข้อให้เขียน:

ต้องตรวจ:
ตรวจเพื่อรู้อะไร:
ถ้าผลเป็น A → ทำอะไรต่อ:
ถ้าผลเป็น B → ทำอะไรต่อ:

ตัวอย่าง:

«ต้องตรวจว่า Interface ปัจจุบันถูกใช้งานที่ไหนบ้าง
เพื่อป้องกันการเปลี่ยนโดยทำให้ consumer เดิมพัง

ถ้าพบว่าใช้เฉพาะ module X → เปลี่ยนได้โดยตรง
ถ้าพบว่าใช้หลาย module → ต้องออกแบบ compatibility ก่อน»

ห้ามเรียกสิ่งนี้ว่า “implementation”

---

6. Dependency ที่ต้องรู้ก่อน

ตอบว่า:

«มีอะไรที่ Phase นี้ “ต้องพึ่ง” ก่อนจึงจะเริ่มได้?»

แบ่งเป็น:

Known

- รู้แล้วว่า...

Unknown

- ยังไม่รู้ว่า...

Blocking

- ถ้าไม่รู้เรื่องนี้ จะยังทำ Phase ต่อไม่ได้

Non-blocking

- ยังไม่รู้ก็เริ่มงานส่วนอื่นได้

---

7.ศัพท์เฉพาะที่ Agent ใช้

ห้ามเอาศัพท์เทคนิคไปกระจายทั่วคำอธิบาย

ให้รวบไว้ตรงนี้แทน

ศัพท์| แปลเป็นภาษาคน| จำเป็นต้องรู้ไหม
X| หมายถึง...| จำเป็น
Y| หมายถึง...| ไม่จำเป็นสำหรับการตัดสินใจ
Z| หมายถึง...| เอาไว้ตอน implementation

หลักคือ:

«ถ้าเอาศัพท์ออกแล้วคนยังเข้าใจสิ่งที่ต้องทำได้ ให้เอาศัพท์ออกจากส่วนหลัก»

---

8. ลำดับการทำงานจริง

สุดท้ายสรุปเป็น Flow เดียว:

«ตรวจสอบ A
↓
ตัดสินใจ C/D
↓
สร้าง B
↓
เปลี่ยน E
↓
ทดสอบ F
↓
ตรวจผล
↓
พร้อมเข้าสู่ Phase ถัดไป»

ห้ามใส่ขั้นตอนที่ไม่ได้จำเป็นต่อการเดินงานจริง

---

9. Definition of Ready

ก่อนเริ่ม Phase นี้ ต้องตอบ “ใช่” ให้กับข้อที่จำเป็น:

- เรารู้ว่าต้องสร้าง / เปลี่ยนอะไร
- รู้ว่าอะไรเป็น dependency
- รู้ว่าจุดไหนต้องตัดสินใจ
- ตรวจสอบข้อมูลที่ใช้ตัดสินใจแล้ว
- ไม่มี Unknown ที่เป็นตัว Block งาน
- รู้ว่าผลลัพธ์ที่คาดหวังคืออะไร

ถ้ายังไม่ครบ ให้หยุดและบอกว่า:

«Phase นี้ยังไม่ Ready

สิ่งที่ต้องเคลียร์ก่อนคือ: ...»

---

10. รายงานสำหรับคนตัดสินใจ

จบด้วยรูปแบบนี้เสมอ:

ตอนนี้เรารู้อะไร

...

ตอนนี้เราต้องทำอะไร

...

ตอนนี้เราต้องตัดสินใจอะไร

...

ตอนนี้เราต้องตรวจอะไร

...

สิ่งที่ยังไม่ควรทำ

...

ขั้นตอนถัดไปที่แนะนำ

...

---

กฎป้องกัน Agent อธิบายยากเกินจำเป็น

เมื่อเขียนคำอธิบาย ให้ถามตัวเองทุกครั้ง:

«“ถ้าตัดศัพท์ technical ออก คนยังรู้ไหมว่า Agent กำลังจะทำอะไร?”»

ถ้า ไม่รู้ → เขียนใหม่

และทุกครั้งที่เขียนว่า:

- architecture
- abstraction
- orchestration
- pipeline
- adapter
- interface
- state
- contract
- migration
- refactor
- validation
- integration

ให้ตรวจว่ามีประโยคตามหลังที่แปลเป็นภาษาคนหรือไม่

ตัวอย่าง:

ไม่ดี:

«เราจะ refactor orchestration layer เพื่อ decouple state management»

ให้เขียนเป็น:

«เราจะเปลี่ยนส่วนที่ควบคุมลำดับการทำงาน เพื่อไม่ให้ส่วนนี้ผูกติดกับการเก็บสถานะมากเกินไป»

จากนั้นค่อยใส่ศัพท์:

«ศัพท์เทคนิค: refactor / decoupling / orchestration»

---

สิ่งที่ห้ามทำ

ห้าม:

- เริ่มแก้ code ทันที
- dump implementation detail ก่อนอธิบายเป้าหมาย
- ทำให้ “ข้อสันนิษฐาน” ดูเหมือน “ข้อเท็จจริง”
- ทำให้ “คำแนะนำ” ดูเหมือน “ข้อสรุป”
- ซ่อน decision point ไว้ในย่อหน้ายาว
- รวม “ต้องตรวจสอบก่อน” กับ “สิ่งที่ต้อง implement”
- เพิ่มงานที่ยังไม่จำเป็นต่อ Phase นี้
- สร้างแผนที่ดูสมบูรณ์แต่ยังมี unknown สำคัญซ่อนอยู่

---

กฎสำคัญที่สุด

ก่อนตอบ ให้คิดตามลำดับนี้:

«Goal → Work → Decision → Verification → Dependency → Execution»

ไม่ใช่:

«Technical Concept → Architecture → Implementation → Explanation»

หน้าที่ของคุณคือทำให้คนอ่านสามารถตอบได้ทันทีว่า:

«“แล้วเราต้องทำอะไรต่อ?”»

โดยไม่ต้องแปลศัพท์ technical เอง
